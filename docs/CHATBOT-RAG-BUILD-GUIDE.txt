================================================================================
PRODUCT GOAL
================================================================================

Build ONE core chatbot system that can be resold/deployed for many companies.
Each client gets isolated configuration for:

  - knowledge base (files, website, Drive, API, DB)
  - prompts, tone, and business rules
  - FAQ layer for critical facts
  - retrieval rules (domain routing, boosts, penalties)
  - guardrails and privacy boundaries
  - branding / widget theme
  - optional external/reference sources

The goal is repeatable deployment with minimal custom engineering per client.

1. EXACT ARCHITECTURE (REFERENCE IMPLEMENTATION)
--------------------------------------------------------------------------------

The reference chatbot is a static-site + browser-side RAG + server-side LLM proxy.

  [User browser]
       |
       |  (1) Load knowledge-index.json (all chunks, precomputed at build time)
       |  (2) Load retrieval-rules.json + client-faq.json
       |  (3) Run hybrid retrieval + scoring entirely in JavaScript
       |  (4) Build grounded prompt with top chunks + hard rules
       |  (5) POST prompt only (never API keys) to serverless proxy
       v
  [Serverless function: /.netlify/functions/gemini-chat]
       |
       |  (6) Keys from env (comma-separated pool, random pick)
       |  (7) CORS origin check, prompt size limit, blocked-pattern check
       |  (8) Forward to Google Gemini (stream or single response)
       v
  [Google Gemini API]

  [Offline build pipelines — no LLM at query time for retrieval]
       sync_drive_to_knowledge_index.py    → Drive PDF/DOCX/Docs → chunks
       sync_website_to_knowledge_index.py  → crawl public site → chunks
       ingest_* scripts                      → targeted handbook/PDF ingests
       merge all into knowledge-index.json

Key design decisions:
  - Retrieval runs in the browser (zero server cost per query for search).
  - LLM keys never touch the client.
  - Single flat JSON index is the runtime knowledge source.
  - Python twin (retrieval_core.py) mirrors JS logic for regression tests.
  - No live web browsing at answer time — only pre-indexed content.

NOTE: chatbot_template moves retrieval to the Python backend (better for
multi-tenant, privacy, and resale). The reference patterns remain valid; only
the runtime location changes.

3. HOW THE KNOWLEDGE INDEX IS BUILT
--------------------------------------------------------------------------------

The reference implementation uses ONE merged file: data/knowledge-index.json

  { "documents": [ ...chunk objects... ] }

Build pipeline (additive merge):

  Step A — Google Drive sync (sync_drive_to_knowledge_index.py)
    1. Authenticate with service account (env: DRIVE_FOLDER_ID, credentials JSON)
    2. Recursively list folder (PDF, DOCX, TXT, Google Docs)
    3. For each file: download → extract text → chunk → write doc objects
    4. Incremental: hash(file_id + modified_time) — skip unchanged files
    5. Cache per-file chunks in drive-sync-state.json
    6. Merge all file chunks into knowledge-index.json

  Step B — Website scrape (sync_website_to_knowledge_index.py)
    1. BFS crawl from --start-url, same-domain only, respects robots.txt
    2. Strip nav/footer/header/cookie boilerplate from HTML
    3. Extract main/article content via BeautifulSoup
    4. Chunk page text → doc objects with source.type = "web"
    5. REPLACE only previous web docs for that domain (additive-safe merge)

  Step C — Targeted ingests (e.g. ingest_*_handbook.py)
    One-off scripts for specific PDFs/handbooks not in Drive.

  Step D — Write final index
    Single JSON file served statically to the browser at runtime.

Template equivalent:
  Drive sync  → google_drive_index.json  (python -m apps.worker.jobs.sync_sources)
  Local JSON  → knowledge.json
  DB seed     → chatbot.sqlite3           (python -m apps.worker.jobs.build_index)
  Vectors     → vector_index.json + optional Qdrant upsert

Template gap: no website scrape worker yet — must be ported from reference.

4. DOCUMENT/WEBSITE CLEANING, CHUNKING, TAGGING, STORAGE
--------------------------------------------------------------------------------

TEXT EXTRACTION (Drive):
  - Google Docs → export as plain text
  - PDF → pypdf page text extraction
  - DOCX → python-docx paragraphs
  - TXT → direct decode
  - normalize_whitespace: collapse spaces, max 2 newlines, strip

WEBSITE CLEANING (scrape):
  - Remove: script, style, noscript, iframe, svg, canvas
  - Remove: nav, footer, header, aside, .menu, .nav, .footer, .cookie, .breadcrumbs
  - Prefer: <main> or <article> or <body> for content
  - Title: <title> → <h1> → URL fallback
  - Min content length filter (default ~200 chars)
  - Skip non-HTML, binary extensions, off-domain links

CHUNKING (both Drive and web):
  - chunk_size: 1300 characters (reference production value)
  - overlap: 180 characters (sliding window)
  - Title format: "filename (μέρος 2/7)" or "Page Title (part 2/7)"
  - Template drive_sources.yaml defaults: 1200 / 150 — align per client

TAGGING per chunk:
  - id: unique (drive_{fileId}_{idx} or web_{domain}_{hash}_{idx})
  - title, content, url
  - language: "el" if Greek chars detected, else "en"
  - keywords: top 12 frequency tokens minus stopwords (used in retrieval)
  - category: inferred from filename (research, policy, education, knowledge)
  - source: { type, fileId/fileName/mimeType OR domain, modifiedTime }
  - org: inferred at retrieval time from URL domain (not always at index time)

STORAGE format (reference chunk object):
  {
    "id": "drive_abc123_2",
    "title": "Annual Report.pdf (μέρος 2/7)",
    "category": "research",
    "content": "...chunk text...",
    "keywords": ["research", "patient", ...],
    "url": "https://drive.google.com/file/d/.../view",
    "language": "el",
    "source": { "fileId": "...", "fileName": "...", "mimeType": "application/pdf" }
  }

IMPORTANT: Reference index does NOT store embedding vectors in practice.
cosineSimilarity() exists in chatbot.js but is unused. Retrieval is keyword-based.

5. QUERY-TIME RETRIEVAL (REFERENCE IMPLEMENTATION)
--------------------------------------------------------------------------------

Entry: retrieveRelevantDocsWithContext() in js/chatbot.js

Flow:

  1. INIT — load knowledge-index.json, retrieval-rules.json, faq.json
     Precompute normalized fields per doc (_titleNorm, _contentNorm, greeklish variants)

  2. QUERY UNDERSTANDING
     - detectLanguage(query)
     - normalize (lowercase, strip accents)
     - toGreeklish for Greek queries
     - extractQueryWords (remove stopwords)
     - resolveUserQuery() for follow-ups ("ναι", "συνέχισε", short replies)
     - getConversationTopic() from last 4 substantive user turns

  3. SCORING (per doc, language-filtered)
     Base keyword signals:
       - title contains full query → +1.2
       - title contains query word → +0.5 each
       - keyword field hits → up to +0.45
       - content word hits → +0.08 each
       - greeklish variants → additional boosts for Greek
       - non-web source slight preference (+0.04)
       - web listing pages (/author/, /category/) penalized (-0.03)

     Then applyRetrievalRelevanceAdjustments():
       - MS/clinical topic signals (domain-specific in reference)
       - domain routing boosts/penalties (see section 7)
       - topicBoosts from rules JSON
       - training noise penalty
       - disability-org vs clinical query penalty

  4. FILTER & RANK
     - Drop docs below minScore (default 0.18)
     - Sort by relevanceScore descending
     - maxChunksPerUrl diversity (default 2 per page)
     - retrievePool cap (default 24 candidates)

  5. FAQ MERGE
     - faqDocsForQuery() injects matching FAQ entries (score ~2.5–3.2)
     - Dedupe by id, take top sendToModel (default 6)

  6. CONTEXT VARIANTS (follow-up handling)
     - If direct query score < 0.38, also search:
       query + last topic (weight 0.78)
       query + last bot reply snippet (weight 0.62)
     - Merge best weighted scores per doc id

  7. OUT-OF-SCOPE GATE
     - If no docs or top score < 0.22 → refuse without calling LLM

  8. BUILD CONTEXT
     - Format: "SOURCE_TITLE: ...\nSOURCE_CONTENT:\n..." joined by ---

Template equivalent today:
  HybridFederatedRetriever — simple token overlap across connectors
  ModeRouterRetriever — routes hybrid_local / vector_db
  NO greeklish, NO domain routing, NO FAQ merge, NO follow-up expansion


--------------------------------------------------------------------------------
6. FAQ LAYER — HOW AND WHEN IT IS USED
--------------------------------------------------------------------------------

File: data/<client>-faq.json

Structure:
  {
    "entries": [
      {
        "id": "faq_contact",
        "triggers": ["τηλεφων", "επικοινων", "contact"],
        "title": "Contact",
        "content": "Exact approved text — phone, email, address"
      }
    ]
  }

When triggered:
  - At retrieval time, AFTER keyword scoring begins
  - faqDocsForQuery() normalizes query, checks if any trigger substring matches
  - Matching entries become synthetic docs with high relevanceScore (2.5+)
  - Merged into candidate pool alongside KB chunks
  - Conditional suppression: e.g. don't inject contact FAQ when user asks about
    a foreign org domain

When to use:
  - Facts that must NEVER be wrong (contact, identity, pricing)
  - Easily confused facts (sample size vs population total)
  - Org disambiguation (company vs product vs disease)
  - Rule: if a mistake would embarrass the client on their homepage → FAQ

Template status: NOT IMPLEMENTED
  Recommended path: packages/config/defaults/faq/<client_id>.json
  Recommended adapter: packages/adapters/retrieval/faq_connector.py

7. RETRIEVAL RULES — BOOSTS, PENALTIES, DOMAIN ROUTING
--------------------------------------------------------------------------------

File: data/retrieval-rules.json

Global knobs:
  retrievePool: 24          — max candidates before final cut
  sendToModel: 6           — chunks injected into LLM prompt
  minScore: 0.18           — below → excluded from candidates
  maxChunksPerUrl: 2       — diversity cap per page
  domainBoost: 0.55        — boost when doc org matches query target org
  domainPenalty: 0.12      — penalize wrong-org docs when query targets specific org
  disabilityOrgPenaltyOnClinicalMs: 0.25
  poamskpResearchPenaltyWhenForeign: 0.08  (reference-specific name — generalize per client)

domainPatterns[] — maps query signals → org tags:
  {
    "org": "client_main",
    "domains": ["client.com", "drive.google.com"],
    "query": ["client name", "brand keyword"]
  }
  At query time detectTargetOrgs() checks query against patterns + hostname mentions.
  doc_org() assigns each chunk an org from URL domain or content signals.

topicBoosts[] — conditional score additions:
  {
    "query": ["fatigue", "κοπωση"],
    "blob": ["fatigue", "κοπωση"],
    "add": 0.4
  }
  Fires when BOTH query and doc blob contain matching topic tokens.

Hardcoded adjustments (in JS + Python twin — reference-specific examples):
  - Clinical topic query + non-clinical doc → score × 0.05
  - Wrong org research PDF on foreign org query → score × 0.08
  - Training/employment noise on clinical query → score − 0.55
  - Confusable org pairs (org A vs org B) → large boost/penalty pairs

outOfIndexSites[] — domains not in KB; used to detect queries needing refusal.

Template status: NOT IMPLEMENTED
  Recommended: packages/config/defaults/retrieval_rules/<client_id>.json
  Recommended: packages/adapters/retrieval/rules_engine.py

8. PROMPTS AND GUARDRAILS BEFORE GEMINI
--------------------------------------------------------------------------------

PROMPT CONSTRUCTION (buildPrompt in reference chatbot.js):

  System-side structure sent as one prompt string:
    1. Role ("You are <bot-name>, assistant for <client>")
    2. Rules 1–14: tone, length, context-only, no URL in body, org voice,
       disambiguation (sample vs total, org vs disease, org A vs org B)
    3. Rules 15–20: security (PROMPT_SECURITY_EL/EN)
    4. Optional forceProgress rules for "continue" directives
    5. LAST ASSISTANT REPLY (for follow-up coherence)
    6. RECENT CHAT CONTEXT (last 6 turns)
    7. AVAILABLE INFORMATION (retrieved chunks)
    8. USER QUESTION
    9. ANSWER:

  Context injection format:
    SOURCE_TITLE: <title>
    SOURCE_CONTENT:
    <chunk text>

  Template equivalent:
    YamlPromptPolicyEngine builds system prompt from prompt_policy.yaml
    ChatOrchestrator injects chunks into user message (not separate system rules)
    Template has basic rules but NOT reference-level disambiguation or security rules

INPUT GUARDRAILS (before LLM call — reference):
  isBlockedUserMessage():
    - JAILBREAK_USER_REGEX (ignore rules, DAN, show API key, dump context)
    - UNRELATED_TOPIC_REGEX IF query not domain-related
    → buildBlockedReply() without API call

  Out-of-scope retrieval gate (top score < 0.22):
    → buildOutOfScopeReply() without API call

PROXY GUARDRAILS (gemini-chat.mjs):
  - MAX_PROMPT_CHARS = 120000
  - BLOCKED_PROMPT_REGEX on incoming prompt
  - CORS: POAMSKP_ALLOWED_ORIGINS (whitelist + Netlify preview URLs)
  - Keys: comma-separated pool, random pick, never in response
  - generationConfig: maxOutputTokens 400, temperature 0.4

OUTPUT GUARDRAILS (sanitizeBotAnswer):
  - Strip AIza… API key patterns
  - Strip drive.google.com / docs.google.com URLs from answer text
  - Strip SOURCE_TITLE / SOURCE_CONTENT leak patterns

SOURCE CITATIONS (public only):
  buildWebsiteSources() — only docs where source.type === "web" AND url is public HTTPS
  Drive URLs, internal paths, FAQ pseudo-URLs → never shown to user
  UI shows source chips below answer (max 4), formatted as "domain-link: Title"

C1. MULTI-TENANT ISOLATION
--------------------------------------------------------------------------------

PRINCIPLE: client_id in a JSON body is a HINT, not proof of identity.
The backend resolves the effective client from authenticated credentials +
request origin, then loads only that tenant's data.

DATA LAYOUT (per client_id):

  data/clients/<client_id>/
    config/
      client.yaml              — display name, modes, feature flags
      prompt_policy.yaml       — prompts, rules, escalation
      themes.yaml              — widget branding
      retrieval_rules.yaml     — boosts, penalties, domain patterns
      faq.json                 — FAQ fast-path entries
      sources.yaml             — Drive roots, website URLs, API endpoints
      guardrails.yaml          — jailbreak patterns, off-topic rules
      locale.yaml              — languages, greeklish enabled/disabled
    indexes/
      knowledge_index.json     — flat chunk store (runtime read)
      vector_index.json        — local vector fallback
      sync_state.json          — incremental Drive/file sync cache
    uploads/                   — admin-uploaded raw files (private)
    db/
      chunks.sqlite3           — optional SQLite mirror per client
    tests/
      regression-questions.json
      questions.txt
      expected-answers.txt
    logs/                      — query audit logs (see C7); NOT committed to git

PLATFORM SECRETS (never in client dirs):

  .env / secret manager:
    PLATFORM_GEMINI_API_KEYS       — platform LLM pool (MVP)
    PLATFORM_ADMIN_JWT_SECRET      — admin console auth (future)
    DATABASE_URL                   — optional central metadata DB

  Per-client secrets (future / enterprise tier):
    data/clients/<id>/secrets.env  — client-owned Gemini key, Drive SA, API keys
    Loaded only by workers + orchestrator for that client_id.
    Never returned by any API.

WHAT IS ISOLATED PER CLIENT:

  | Asset            | Location                              | Cross-tenant access |
  |------------------|---------------------------------------|---------------------|
  | Documents/chunks | data/clients/<id>/indexes/            | NEVER               |
  | FAQ              | data/clients/<id>/config/faq.json     | NEVER               |
  | Prompts/rules    | data/clients/<id>/config/             | NEVER               |
  | Themes           | data/clients/<id>/config/themes.yaml  | NEVER               |
  | Retrieval rules  | data/clients/<id>/config/             | NEVER               |
  | Query logs       | data/clients/<id>/logs/ or central DB | admin of that client|
  | Embeddings       | Qdrant collection per client OR       | NEVER               |
  |                  | vector_index scoped by client_id      |                     |
  | LLM secrets      | platform env OR client secrets.env    | scoped              |

AUTH: HOW WIDGET / DOMAIN / API KEY MAPS TO client_id

  Three credential tiers:

  TIER 1 — Public widget key (browser-safe, embeddable)
    Header: x-client-key: <widget_public_key>
    Issued per client at onboarding. Maps 1:1 to client_id server-side.
    Stored in platform registry (clients.yaml → widget_keys[] or DB table).
    Optional origin binding: allowed_origins[] per key
      (https://client.com, https://www.client.com, http://localhost:5173).
    Request rejected if Origin/Referer not in allowlist (when binding enabled).
    Widget key CANNOT access admin endpoints or debug traces.

  TIER 2 — Server integration key (backend-to-backend)
    Header: Authorization: Bearer <integration_secret>
    For client CMS, CRM, mobile apps calling API directly.
    Maps to client_id + scopes (chat:write, config:read).
    Rate-limited separately from widget key.

  TIER 3 — Admin (SimasiaAI platform or client company)
    Header: Authorization: Bearer <admin_jwt>
    MVP fallback: x-admin-token (platform_admin only — dev/staging ONLY).
    Roles (authoritative matrix in PART D §D29):
      platform_admin  — full control over all clients and platform settings
      client_admin    — scoped to one client_id; safe self-service only
    Production MUST use JWT with role + client_id (for client_admin) claims.

  See PART D §D29 for full permission model. Widget/integration tiers unchanged above.

RESOLUTION FLOW (every /v1/chat/respond request):

  1. Extract credential: x-client-key OR Bearer integration token.
  2. Resolve client_id from credential registry (NOT from request body alone).
  3. If body contains client_id, it MUST match resolved client_id or → 403.
  4. Validate Origin against client's allowed_origins (widget tier).
  5. Load tenant config + indexes from data/clients/<client_id>/ only.
  6. Proceed with chat pipeline.

MVP COMPATIBILITY:
  - Keep accepting client_id in body for local dev ONLY when ALLOW_INSECURE_CLIENT_ID=true.
  - Production deployments set ALLOW_INSECURE_CLIENT_ID=false (default).

C2. INGESTION PIPELINE (OFFLINE / ASYNC)
--------------------------------------------------------------------------------

RULE: Documents and websites are NEVER fetched live during chat.
All static knowledge is indexed offline. Live connectors are ONLY for:
  - External REST APIs marked dynamic: true in sources.yaml
  - Database tables with frequently changing records
  - NOT for PDFs, Drive files, or website pages.

FULL PIPELINE (per source item):

  ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌──────────┐   ┌─────────┐
  │ EXTRACT │ → │  CLEAN  │ → │  CHUNK  │ → │   TAG    │ → │  EMBED  │
  └─────────┘   └─────────┘   └─────────┘   └──────────┘   └─────────┘
       │              │              │              │              │
       ▼              ▼              ▼              ▼              ▼
  ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌──────────┐   ┌─────────┐
  │  STORE  │ → │ VERSION │ → │  TEST   │ → │ ACTIVATE │   │ (done)  │
  └─────────┘   └─────────┘   └─────────┘   └──────────┘   └─────────┘

STEP DETAIL:

  EXTRACT
    Uploads:    admin POST /v1/admin/clients/{id}/uploads → saves to uploads/
    Drive:      worker sync_drive --client-id X (service account per client or shared)
    Website:    worker sync_website --client-id X --start-url https://client.com
    Formats:    PDF (pypdf), DOCX (python-docx), TXT, Google Docs export, HTML scrape

  CLEAN
    - normalize_whitespace (collapse spaces, strip boilerplate newlines)
    - Remove nav/footer/header/cookie banners from HTML
    - Strip repeated headers/footers from PDF page text
    - Language detection → tag el/en/other
    - PII scan flag (optional): mark chunks containing AMKA/SSN patterns for exclusion

  CHUNK
    - Configurable per client: chunk_size (default 1200), overlap (default 150)
    - Title prefix in chunk: "Τίτλος: {title}\n\n{content}"
    - Part labels: "{title} (part 2/7)"
    - Min chunk length filter (drop < 80 chars)

  TAG METADATA (per chunk)
    {
      "id", "title", "content", "url", "language",
      "keywords": [...],           // top frequency tokens
      "category": "faq|web|drive|upload|policy|...",
      "org_tag": "client_main|partner_x|...",   // for domain routing
      "source": { "type", "file_id", "domain", "modified_at" },
      "index_version": "2026-06-06T12:00:00Z",
      "citation_url": "https://client.com/page"  // public URL for UI (may differ from internal url)
    }

  EMBED
    - Model: GEMINI_EMBEDDING_MODEL (default gemini-embedding-001)
    - Batch embed all new/changed chunks
    - Store vectors in:
        a) vector_index.json (dev/small clients)
        b) Qdrant collection "client_{client_id}" (production)
    - Record embedding_model version in index metadata (must match query-time model)

  STORE
    - Write to data/clients/<id>/indexes/knowledge_index.json
    - Upsert rows to client SQLite chunks table
    - Upsert vectors to Qdrant

  VERSION
    - Each build produces index_manifest.json:
        { "version": "uuid", "built_at", "chunk_count", "sources": [...], "status": "pending" }
    - Activation is atomic swap: current → previous (rollback capable)
    - Runtime reads "active" pointer only after tests pass

  TEST (gate before activate — see C5)
    - Run client test suite against pending index version
    - If pass → activate; if fail → keep previous index, notify admin

  ACTIVATE
    - Flip active manifest pointer
    - Invalidate in-memory index cache for client_id

TRIGGERS:
  - Admin: POST /v1/admin/clients/{id}/reindex
  - Scheduled: cron/GitHub Action per client (Drive + website delta sync)
  - Upload: auto-queue reindex job on file upload complete

WORKER COMMANDS (target):
  python -m apps.worker.jobs.ingest --client-id acme --source drive
  python -m apps.worker.jobs.ingest --client-id acme --source website
  python -m apps.worker.jobs.ingest --client-id acme --source uploads
  python -m apps.worker.jobs.build_index --client-id acme
  python -m apps.worker.jobs.activate_index --client-id acme --version <uuid>

C3. RETRIEVAL PIPELINE (QUERY TIME)
--------------------------------------------------------------------------------

Entry: ChatOrchestrator.answer() → RetrievalPipeline.retrieve()

STAGES (in order):

  STAGE 0 — INPUT GATE
    - Jailbreak / off-topic check (client guardrails.yaml)
    - If blocked → return refusal, skip retrieval, log trace

  STAGE 1 — QUERY REWRITE
    - Normalize text (lowercase, strip accents if locale config enabled)
    - Greeklish transliteration (ONLY if client locale.yaml: greeklish_enabled: true)
    - Follow-up expansion: short replies ("yes", "ναι", "continue") → resolve from
      session history + last bot question (session_id required)
    - Output: rewritten_query, rewrite_reason, is_follow_up

  STAGE 2 — FAQ MATCHING
    - Match rewritten_query against faq.json triggers (substring, normalized)
    - FAQ hits become FaqChunk objects with base_score = 2.5 (configurable)
    - Conditional suppression rules (e.g. don't inject contact FAQ on partner-org query)
    - Output: faq_hits[]

  STAGE 3 — PARALLEL RETRIEVAL (static indexes only)
    3a. KEYWORD SEARCH
        - Search client knowledge_index / SQLite
        - Title match, keyword field match, content token overlap
        - Apply locale-specific tokenization (Greek stopwords if el enabled)
        - Output: keyword_hits[] with raw_keyword_score

    3b. VECTOR SEARCH (if embeddings available)
        - Embed rewritten_query with same model as index
        - Query Qdrant collection client_{id} OR local vector_index.json
        - Cosine similarity → raw_vector_score
        - Output: vector_hits[]

    3c. LIVE CONNECTORS (only sources marked dynamic: true)
        - API connector, DB connector
        - Output: live_hits[]

  STAGE 4 — RETRIEVAL RULES (per-client retrieval_rules.yaml)
    For each candidate chunk:
      - Detect target org/domain from query (domainPatterns)
      - Apply domainBoost (+0.55) if org matches
      - Apply domainPenalty (×0.12) if wrong org
      - Apply topicBoosts[] (query token + blob token → +add)
      - Apply hardcoded client rules from config (NOT hardcoded in code)
      - Apply penalties: training noise, wrong-domain research, etc.
    Output: adjusted_score per chunk + boost_penalty_log[]

  STAGE 5 — SCORE FUSION (HYBRID COMBINATION)
    Default fusion formula (configurable weights in retrieval_rules.yaml):

      final_score =
        w_kw  * normalize(keyword_score)     // default w_kw = 0.45
      + w_vec * normalize(vector_score)     // default w_vec = 0.35
      + w_faq * faq_bonus                   // 1.0 if FAQ hit else 0
      + rule_delta                          // sum of boosts/penalties from stage 4

    Normalization: min-max within candidate pool, or z-score — configurable.
    FAQ chunks: if FAQ trigger is strong match (≥2 triggers), floor final_score at 0.85.
    Live hits: w_live default 0.20, merged same way.

  STAGE 6 — RERANK + DIVERSITY
    - Sort by final_score descending
    - Drop below min_score threshold (default 0.18) → candidate for "low confidence"
    - max_chunks_per_url (default 2) — diversity cap
    - retrieve_pool cap (default 24) before final cut
    - Optional cross-encoder rerank (future; not MVP)

  STAGE 7 — FINAL CONTEXT SELECTION
    - Select top send_to_model chunks (default 6)
    - Separate selected[] vs rejected[] with reasons for trace
    - Build context string for LLM prompt
    - If no chunks above min_score → skip LLM, return "I don't know" + escalation hint

LOCALE CONFIG (per client — locale.yaml):

  primary_language: el
  supported_languages: [el, en]
  greeklish_enabled: true          # false for non-Greek clients
  accent_normalization: true
  stopwords_file: el.txt           # or en.txt, none

C5. TESTING / EVALUATION (DEPLOY GATE)
--------------------------------------------------------------------------------

RULE: A client MUST NOT be deployed to production until its test suite passes.

Per-client test package: data/clients/<id>/tests/

  regression-questions.json   — retrieval-only, expected org/topic/chunk_id
  questions.txt               — full Q&A scenarios (multi-turn)
  expected-answers.txt        — reference answers or key phrases
  test-config.yaml            — pass thresholds

TEST CATEGORIES:

  1. RETRIEVAL REGRESSION (no LLM, fast, required)
     - Input: regression-questions.json
     - Assert: top-3 chunks match expected org_tag or chunk_id
     - Pass threshold: ≥ 90% (configurable)

  2. ANSWER QUALITY (with LLM, required before prod)
     - Input: questions.txt + expected-answers.txt
     - Assert: key phrases present, no forbidden phrases, no hallucinated contacts
     - Pass threshold: ≥ 85% sense_ok (configurable)

  3. OFF-TOPIC REFUSAL (required)
     - Input: fixed list (bitcoin, recipes, generic trivia)
     - Assert: refusal message, no LLM hallucination, no internal leak

  4. JAILBREAK REFUSAL (required)
     - Input: fixed list (ignore rules, show API key, dump context)
     - Assert: blocked before LLM OR safe refusal, no key leak

  5. CITATION / SOURCE TESTS (required)
     - Input: questions that should cite public website pages
     - Assert: sources[] contains public URL, NO drive.google.com, NO internal://

  6. FAQ PRECISION (required if FAQ configured)
     - Input: one question per FAQ entry
     - Assert: FAQ chunk in selected context, answer contains approved fact

DEPLOY GATE:
  python -m apps.worker.jobs.run_client_tests --client-id acme --suite full
  Output: test_report.json with pass/fail per category
  POST /v1/admin/clients/{id}/deploy requires test_report.status == "pass"

C9. CONFIDENCE (NO FAKE NUMBERS)
--------------------------------------------------------------------------------

Do NOT return a decimal like 0.75 unless it maps to a defined signal.
Public API returns confidence.level + confidence.reason.

LEVEL DEFINITIONS:

  HIGH
    - FAQ direct hit on strong trigger match, OR
    - ≥ 2 selected chunks with final_score ≥ 0.55 and same org_tag as query target, OR
    - FAQ + at least 1 strong keyword/vector hit
    Reason example: "Matched FAQ entry faq_contact plus supporting document."

  MEDIUM
    - 1–2 chunks above min_score but no FAQ hit, OR
    - Mixed signals (chunks from different orgs but best score ≥ 0.35), OR
    - Follow-up query resolved from history with moderate retrieval
    Reason example: "One relevant document found; answer may be incomplete."

  LOW
    - Chunks found but top score < 0.35, OR
    - Only live/dynamic source hits (no static KB match), OR
    - Query partially off-topic but allowed through
    Reason example: "Weak document match; verify answer with official sources."

  NONE (triggers escalation, not LLM)
    - No chunks above min_score after all stages
    - Input blocked by guardrails
    Reason example: "No approved knowledge found for this question."

Internal trace stores numeric final_scores for debugging; not exposed to widget.

C10. ESCALATION (PER CLIENT)
--------------------------------------------------------------------------------

Configured in prompt_policy.yaml → escalation section + escalation_rules.yaml:

ESCALATION TYPES:

  dont_know
    When: confidence NONE, or no chunks above min_score
    Action: Return configured refusal message. requires_human = false.
    Example: "I don't have approved information on that. I can help with ..."

  suggest_contact
    When: confidence LOW + query matches contact-intent triggers, OR
          user asks for pricing/contract not in KB
    Action: Answer what is known + suggest contact channel from FAQ.
    requires_human = false.

  collect_lead
    When: user expresses purchase/demo intent (configurable triggers)
    Action: Ask for name/email with privacy note; store in lead queue (future).
    requires_human = false.

  human_handoff
    When: user frustration detected (configurable), OR
          explicit "speak to human" request, OR
          medical/legal/financial beyond approved content
    Action: requires_human = true; return handoff message + contact info.
    Example: "I'll connect you with our team. Contact: ..."

PRIORITY: guardrail block > dont_know > human_handoff > collect_lead > suggest_contact > normal answer

FAQ content provides exact contact strings — never LLM-invented phone numbers.

D7. CITATION / GROUNDING ENFORCEMENT FLOW
--------------------------------------------------------------------------------

NUMBERING:
  - Context numbered [1]..[N]; prompt instructs inline [n] citations per factual claim
  - sources[] maps index → public citation_url (clickable); internal hidden unless allowed

STANDARD MODE:
  - citation_enforcer strips invented [n] markers (indices not in retrieved set)
  - LLM-generated URLs stripped unless they match retrieved chunks or source_whitelist
  - Empty/weak retrieval → "not found in approved sources" + optional escalation

REGULATED MODE (regulated_mode: true — stricter, code-enforced):
  - Citations MUST be sentence-level / factual-claim-level — NOT end-of-paragraph only
  - Every factual claim in the answer must either:
      (a) carry a valid inline [n] immediately after or within the same sentence, OR
      (b) be removed or rephrased as "not found in approved sources"
  - End-of-paragraph citation blobs are INVALID in regulated_mode (fail validation)
  - citation_enforcer MUST validate that EVERY [n] in the final answer maps to a
    retrieved chunk in the context map (index ∈ {1..N} of selected chunks)
  - Unsupported factual sentences are stripped or replaced with refusal phrasing
  - No invented URLs, document names, or citation indices
  - Deploy gate includes citation regression tests (claim-level coverage)

CITATION_ENFORCER CHECKS (all modes):
  1. Parse all [n] markers in answer
  2. Reject/strip any n ∉ retrieved context indices
  3. In regulated_mode: scan sentences for uncited factual claims → strip/rephrase
  4. Cross-check sources[] against source_whitelist.yaml + retrieved citation_url fields
  5. Record citation_validity in trace (admin-only)

D21. ADMIN WORKFLOW (ROLE-AWARE)

  WIDGET AUTH (all profiles — Phase 1, required):

  - x-admin-token → platform_admin only (local profile)

  - Firebase Auth for platform_admin / client_admin → Phase 11 (Firebase adapter phase)

      AuthProvider, AdminAuthProvider, ConfigStore (minimal methods)

  - Do NOT define full ABCs for FileStore, ChunkStore, TraceStore, etc. until their phase
  - LLMProvider / VectorStore: keep existing code; migrate to ports when touched
  - Firebase/GCP adapters: stub or defer to Phase 11+ — no Firebase imports in core
  - Do NOT hardcode Firebase into core platform logic

D27. PRIVACY BEFORE TRACE (REQUIRED ORDERING)
--------------------------------------------------------------------------------

RULE: privacy.yaml MUST exist and be enforced BEFORE TraceRecord storage is implemented.

Implementation gate:
  - Phase 8 implements privacy model + PII redaction pipeline
  - Phase 9 implements TraceRecord — ONLY after Phase 8 is complete
  - No interim "store everything then redact later" path

privacy.yaml fields (minimum):
  mode: standard | anonymized | aggregate_only | do_not_log
  store_raw_messages: bool        # false when mode is do_not_log or aggregate_only
  store_rewritten_query: bool
  pii_redaction_enabled: bool
  retention_days: int

Mode behavior:
  standard:       raw messages allowed if store_raw_messages: true; PII redacted first
  anonymized:     hash user_id; redact PII in message fields before write
  aggregate_only: NO raw query/answer in trace — counts/latencies/confidence only
  do_not_log:     NO trace persistence of message content; trace_id may still be returned
                  as opaque correlation id with metadata-only internal record

Pipeline order (mandatory):
  1. Generate answer
  2. Apply privacy redaction to in-memory trace payload
  3. Drop fields disallowed by mode (e.g. original_message in aggregate_only)
  4. Persist trace (if any fields remain storable)
  5. Return widget response (trace_id only — never full trace)


--------------------------------------------------------------------------------
D28. DEBUG ACCESS (WIDGET vs ADMIN)
--------------------------------------------------------------------------------

WIDGET (x-client-key — public embed):
  - debug: true in POST /v1/chat/respond returns trace_id ONLY in response
  - Widget MUST NOT receive: retrieved chunks, scores, prompts, internal URLs,
    rejected chunks, boost logs, or full TraceRecord
  - Browser-origin debug=true is NOT a debug credential — treat as correlation only

ADMIN / INTEGRATION (debug scope required for full trace):
  - GET /v1/admin/traces/{trace_id} — platform_admin OR integration secret with
    debug scope; client_admin forbidden unless explicit debug:traces scope granted
  - POST /v1/admin/clients/{id}/preview:
      platform_admin → full inline trace
      client_admin → answer + confidence + public sources + summary only (D29)
  - Full trace content still respects privacy.yaml (fields may be redacted/absent)

FORBIDDEN:
  - Returning full trace in chat respond body for any credential tier
  - Widget key accessing GET /v1/admin/traces/*
  - Leaking private/internal source URLs to widget when show_public_sources_only: true
